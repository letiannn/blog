# NAND Flash

---

## 一、NAND Flash 基础知识

### 1.1 存储结构与操作模型

NAND Flash 的存储层次从大到小依次为：**Plane（平面） → Block（块） → Page（页） → Sector（扇区）**。外围电路通过复用数据总线传输地址和命令，以节省引脚。

核心约束——**"写前擦除"（erase-before-write）** 是理解所有 NAND 软件设计的起点：

| 操作 | 最小粒度 | 典型操作耗时 (SLC) | 说明 |
|------|---------|-------------------|------|
| **读取 (Read)** | Page (2KB~16KB) | ~25–50 μs | 可按字节偏移随机读，无需在擦除后执行 |
| **写入/编程 (Program)** | Page (2KB~16KB) | ~200–700 μs | 只能在已擦除区域进行，不允许原地覆盖 |
| **擦除 (Erase)** | Block (64~256 Pages) | ~1–5 ms | 写入前必须执行，会将块内所有位恢复为 1（0xFF） |

> 这种"大擦除、大写入"的物理特性，使得 NAND 不能像磁盘那样原地覆写——软件必须通过**地址映射**和**垃圾回收**来模拟块设备模型。

每个 Page 除了数据区外，还有一个独立的 **OOB (Out-Of-Band) 区域**（又称 Spare Area），用于存放 ECC 校验码、坏块标记等管理信息。这是 NAND 驱动层必须精确处理的细节：读写数据区时必须跳过 OOB 区，保证 512 字节 / 2048 字节等标准扇区对齐。

### 1.2 优缺点总结

NAND Flash 凭借高容量和接口灵活性，在嵌入式存储中占据主导，但与 NOR Flash 存在明显的设计取舍。

**优点：**
- **单位成本极低**：同等容量下价格远低于 NOR Flash，非常适合大容量数据存储
- **读写速度快**：写入与擦除操作比 NOR Flash 快得多
- **容量扩展性好**：从几百 MB 到 TB 级别均可实现
- **非易失、抗震动、低功耗**：适合工业和车载环境

**缺点：**
- **出厂即存在坏块**：NAND 出厂时就可能有坏块，使用过程中还会新增坏块，必须有坏块管理策略
- **擦除次数有限**：SLC 典型 10 万次，MLC 仅 1K–10K 次，磨损均衡必不可少
- **容易出现 bit error**：必须配合 ECC 校验（BCH 或 LDPC），SLC 通常需 1~4 bit ECC，MLC 需更高
- **存在读干扰 (Read Disturb)**：对同一 Block 的大量读取可能改变相邻页的数据位，需周期性刷新
- **操作粒度不对齐**：擦除以 Block 为单位，写入以 Page 为单位，读取以 Sector (512B) 为单位——编程需严格按照三者的访问与边界规则进行，或借助 FTL 屏蔽差异


## 二、开源框架下的 NAND 适配

### 1. Linux 生态（最成熟）

Linux 对 NAND 的支持是**分层最清晰**的：

```
┌─────────────────────────────┐
│  文件系统: UBIFS / JFFS2 / YAFFS2 / SquashFS
├─────────────────────────────┤
│  UBI (Unsorted Block Images): 卷管理、磨损均衡、坏块管理
├─────────────────────────────┤
│  MTD (Memory Technology Device): 原始 NAND 抽象
├─────────────────────────────┤
│  NAND Controller Driver: 芯片厂商驱动 (omap2/onenand/...)
├─────────────────────────────┤
│  硬件: NAND Flash 芯片
└─────────────────────────────┘
```

- **MTD 层**：提供 `read_oob` / `write_oob` / `erase` / `block_isbad` / `block_markbad` 等接口，屏蔽不同 NAND 差异
- **UBI 层**：在 MTD 之上提供逻辑卷管理，自带坏块管理、磨损均衡、原子更新。UBI 是**强烈推荐**的中间层
- **UBIFS**：基于 UBI 的日志结构文件系统，支持写缓存、动态卷大小、压缩。适合大容量 NAND
- **JFFS2**：较老，挂载慢，不适合大容量（>128MB）
- **YAFFS2**：简单，启动快，但无压缩，适合小容量

**Linux 下适配 NAND 的典型流程**：
1. 确认 NAND 芯片型号 → 在设备树（DTB）中配置 `nand-controller` 节点
2. 内核启用 `CONFIG_MTD_NAND`、`CONFIG_MTD_UBI`、`CONFIG_UBIFS`
3. 若芯片无内置 ECC，配置软件 BCH/RS ECC
4. 用户空间用 `ubiattach` / `ubiformat` 初始化，之后 mount UBIFS

### 2. RT-Thread（国产RTOS，生态完善）

RT-Thread 的存储栈设计非常贴合国内嵌入式开发习惯：

```
┌─────────────────────────────┐
│  文件系统: elm-FAT / littlefs / jffs2 / dfs_ramfs
├─────────────────────────────┤
│  FAL (Flash Abstraction Layer): 分区管理、跨 Flash 统一接口
├─────────────────────────────┤
│  MTD NOR / MTD NAND 驱动
├─────────────────────────────┤
│  底层: SPI NAND / Parallel NAND / eMMC 驱动
└─────────────────────────────┘
```

- **FAL 组件**：强烈推荐使用。将 Flash 划分为逻辑分区（如 `nand0_canlog`、`nand0_config`），应用层无需关心物理地址
- **DFS 文件系统层**：可以挂载 littlefs（推荐）或 FAT（需 FTL）
- **Littlefs**：专为裸 Flash 设计的日志结构文件系统，自带磨损均衡、掉电安全，**非常适合 NAND**（需配合 FTL 或直接在 NOR 上用，NAND 上通常需要 FTL 层或 UBI 类似物）
- **RT-Thread 的 NAND 驱动**：通常需要对接 `rt_mtd_nand` 设备框架，实现 `read_page` / `write_page` / `erase_block` / `check_block` / `mark_bad_block`

**注意**：RT-Thread 标准版对 Raw NAND 的 FTL 支持不如 Linux 完善。如果用 NAND，通常有两种路径：
- **路径 A**：外接带 FTL 的 NAND（如 eMMC、SD NAND），对 RTT 来说就是块设备，直接格式化 FAT/littlefs
- **路径 B**：用 Raw NAND + 第三方 FTL（如 FlashDB 的 FTL 层）或自己实现轻量 FTL

### 3. Zephyr（现代物联网RTOS）

Zephyr 的 Flash 子系统设计比较现代：

```
┌─────────────────────────────┐
│  文件系统: LittleFS / FATFS / NVS (Non-Volatile Storage)
├─────────────────────────────┤
│  Flash Map / Flash Area API: 固定分区抽象
├─────────────────────────────┤
│  Flash Controller Driver: 统一 Flash API (flash_read/write/erase)
├─────────────────────────────┤
│  底层: SPI NAND / QSPI NAND / eMMC 驱动
└─────────────────────────────┘
```

- **Flash Map**：通过设备树定义固定分区（如 `storage_partition`），应用用 `flash_area_open()` 访问
- **NVS**：轻量级键值存储，适合配置数据，**不适合高频大数据流**（CAN 日志不适合用 NVS）
- **LittleFS**：Zephyr 官方推荐用于外部 Flash。但注意：LittleFS 本身不处理 NAND 的坏块和 ECC，通常需要：
  - 底层驱动完成 ECC 和坏块跳过
  - 或者使用支持 NAND 的 FTL 层
- **Settings 子系统**：适合存配置，非日志场景

**Zephyr 对 Raw NAND 的支持**：相比 Linux 较弱，社区驱动较少。工业上常用 **SPI NAND** 通过 SPI 接口接入，驱动层需自行处理坏块和 ECC。

### 4. 裸机 / 自研方案

如果不用 OS 或 OS 很轻量，通常需要自研一个**轻量 FTL**：

- **核心数据结构**：
  - 逻辑-物理映射表（L2P Table）：通常用页级映射，为省 RAM 可用块级映射 + 页级缓存
  - 坏块表（BBT）：存于 Flash 固定区域（通常最后几个 Block），双备份
  - 空闲块池：维护可用 Block 列表
- **关键算法**：
  - 磨损均衡：每次分配新块时选擦除次数最少的
  - 垃圾回收：后台或按需搬移有效页、回收无效 Block
  - 掉电恢复：启动时扫描元数据区重建映射表

## 一、两种架构的分层图

### 方案 1：Raw NAND → MTD NAND → FTL → FAL → LittleFS

```
┌─────────────────────────────────────────────┐
│  Layer 5: LittleFS                          │
│  - 文件/目录管理、COW 写时复制、掉电安全        │
│  - 假设底层是"完美块设备"，不感知坏块           │
├─────────────────────────────────────────────┤
│  Layer 4: FAL (Flash Abstraction Layer)     │
│  - 分区表管理：把块设备切成 canlog/config 等   │
│  - 逻辑地址偏移转换                           │
├─────────────────────────────────────────────┤
│  Layer 3: FTL (Flash Translation Layer)     │
│  - L2P 地址映射、坏块管理、磨损均衡、GC、ECC    │
│  - 把"有坏块的 NAND"伪装成"完美块设备"         │
├─────────────────────────────────────────────┤
│  Layer 2: MTD NAND                          │
│  - RT-Thread 设备抽象：read_page/write_page   │
│  - 提供 check_block / mark_badblock 接口      │
├─────────────────────────────────────────────┤
│  Layer 1: Raw NAND (SLC SPI/Parallel)       │
│  - 物理芯片：先擦后写、坏块、P/E 寿命有限       │
└─────────────────────────────────────────────┘
```

### 方案 2：Raw NAND → MTD NAND → YAFFS2

```
┌─────────────────────────────────────────────┐
│  Layer 3: YAFFS2                            │
│  - 文件系统 + 自带 FTL 功能（坏块/均衡/GC/ECC） │
│  - 日志结构顺序追加，直接管理物理 NAND          │
├─────────────────────────────────────────────┤
│  Layer 2: MTD NAND                          │
│  - 标准设备接口，供 YAFFS2 调用               │
│  - YAFFS2 通过它做坏块检测/标记               │
├─────────────────────────────────────────────┤
│  Layer 1: Raw NAND                          │
│  - 物理芯片                                   │
└─────────────────────────────────────────────┘
```

## 二、逐层职责对比

| 层级 | 方案 1 (FTL+FAL+LittleFS) | 方案 2 (YAFFS2) |
|------|--------------------------|----------------|
| **文件系统** | LittleFS 只管文件逻辑，不管物理坏块 | YAFFS2 既管文件逻辑，又管物理坏块/均衡 |
| **FTL 层** | **独立层**：需自己实现或移植（如 Dhara），代码量大，RAM 占用高 | **内嵌在 YAFFS2 内部**：无需独立 FTL |
| **分区管理** | FAL 提供灵活分区（canlog/config/firmware） | **无 FAL**：整片 NAND 就是一个文件系统，或 YAFFS2 内部简单分区 |
| **坏块处理** | FTL 维护 BBT，跳过坏块；FAL 和 LittleFS 完全无感知 | YAFFS2 直接调用 MTD 的 `check_block`/`mark_badblock`，自己维护 |
| **磨损均衡** | FTL 负责物理层均衡；LittleFS 只做逻辑层偏移 | YAFFS2 统一负责 |
| **垃圾回收** | **双重 GC**：LittleFS 整理文件元数据 + FTL 回收物理块 | **单一 GC**：YAFFS2 自己回收无效页 |

---

## 三、关键差异详解

### 1. 坏块管理的归属不同

- **方案 1**：坏块管理在 **FTL 层** 闭环。FTL 向上呈现"0~N 的完美逻辑块"，FAL 和 LittleFS 完全不知道底下有坏块。FTL 必须在初始化时扫描全片建立 BBT，并在运行时维护替换策略。
- **方案 2**：坏块管理在 **文件系统层** 闭环。YAFFS2 自己决定"这个逻辑地址该写到哪个物理块"，遇到坏块直接跳过并更新内部映射。

### 2. 写放大（Write Amplification）风险

- **方案 1**：**双重写放大**。
  - LittleFS 做 COW（写时复制）：改一个文件可能触发元数据级联更新
  - FTL 做 GC：搬移有效页时产生额外写入
  - 两层叠加，对高频小数据（CAN 帧 8~64 字节）极不友好

- **方案 2**：**单一写放大**。
  - YAFFS2 是日志结构，追加写入为主，修改文件也是追加新版本
  - GC 只在空闲块不足时触发，且因为顺序流式写入，大部分 Block 是整块失效，GC 只需擦除无需搬移

### 3. 写入延迟确定性（对 CAN 最关键）

| 场景 | 方案 1 | 方案 2 |
|------|--------|--------|
| 正常写入 | 低（直接追加） | 低（直接追加） |
| LittleFS/YAFFS2 GC | 中（文件元数据整理） | 低（日志结构，GC 轻量） |
| FTL GC | **高且不可预期**（可能搬移几十页） | 无 |
| 坏块替换 | FTL 内部处理，延迟增加 | YAFFS2 内部处理，延迟增加 |

**方案 1 的致命问题**：FTL 的 GC 是物理层行为，可能在任意时刻触发（比如你正在写一帧关键 CAN 数据），导致**写入延迟 spike**，丢帧风险高。

### 4. RAM 与代码体积

| 资源 | 方案 1 | 方案 2 |
|------|--------|--------|
| **代码量** | FTL (~1500行) + FAL + LittleFS ≈ **较大** | YAFFS2 单组件 ≈ **中等** |
| **RAM 占用** | FTL 映射表（1GB NAND 约 4~8KB LUT）+ FAL 表 + LittleFS 缓存 ≈ **20~50KB+** | YAFFS2 内部结构 ≈ **10~30KB** |
| **栈/堆压力** | 多层嵌套，调用栈深 | 层数少，调用栈浅 |

### 5. 分区灵活性

- **方案 1**：✅ **强**。FAL 可以把块设备切成多个独立分区，分别挂不同文件系统（如 `canlog` 挂 LittleFS，`config` 挂 NVS）。
- **方案 2**：❌ **弱**。YAFFS2 通常管理整片 NAND，内部分区机制不如 FAL 灵活。如果需要多个独立区域，需要挂多个 YAFFS2 实例或自行管理。

## 四、针对你的 CAN 高频数据场景的适配度

| 需求 | 方案 1 | 方案 2 |
|------|--------|--------|
| **高频顺序追加** | ⚠️ 能用，但双重 GC 有延迟风险 | ✅ 日志结构天然适合 |
| **小数据包写入** | ❌ 写放大严重（64 字节 → 触发页写入 + 可能 GC） | ✅ 可缓存合并后顺序写入 |
| **不允许丢帧** | ❌ FTL GC 可能导致写入阻塞 | ✅ 延迟更可控 |
| **环形覆盖（FIFO）** | ⚠️ FTL GC + 文件删除触发更多 GC | ✅ 整块失效后回收效率高 |
| **掉电安全** | ✅ LittleFS COW + FTL 双备份 = 强 | ✅ YAFFS2 日志结构 = 强 |
| **调试定位** | ❌ 层数多，出问题要查 FTL/FAL/FS 三层 | ✅ 层数少，问题边界清晰 |
| **长期运行稳定性** | ⚠️ 依赖自研/移植 FTL 的成熟度 | ⚠️ 依赖 YAFFS2 移植质量 |

---

## 五、总结：两种架构的本质区别

> **方案 1 是"通用计算机思维"**：用 FTL 把 NAND 伪装成硬盘，再用通用文件系统管理。层数多、灵活性强，但**不适合高频实时流式写入**。
>
> **方案 2 是"嵌入式专用思维"**：文件系统直接感知 NAND 物理特性，专为 NAND 设计。层数少、路径短，**天然适合顺序追加型数据**。

### 给你的建议

| 你的情况 | 推荐方案 |
|---------|---------|
| 团队有存储开发经验，且需要**多个独立分区**（如同时存 CAN 日志、配置、固件） | 方案 1，但建议用 **eMMC/SD NAND**（自带 FTL）替换 Raw NAND，省去自研 FTL 的风险 |
| 追求**极致性能、低延迟、不丢帧**，且主要是**单一用途**（存 CAN 日志） | **方案 2（YAFFS2）** 或 **裸分区自研环形日志** |
| 想快速出原型，不想碰 FTL | **方案 2** 或换 **eMMC + FAL + LittleFS** |

**如果坚持 Raw NAND + RT-Thread + 高频 CAN 数据，方案 2（YAFFS2）是更合理的架构选择。**


## 结论

1.使用Raw NAND的情况下
- 建议使用YAFFS2的架构

2.更换存储设备为eMMC
- 建议使用FAL + LittleFS的架构
